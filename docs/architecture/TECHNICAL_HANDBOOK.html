SMYou Pro — Technical Handbook

Tài liệu kỹ thuật tổng hợp để bất kỳ lập trình viên nào cũng có thể maintain và vận hành hệ thống — từ kiến trúc, luồng dữ liệu, tới build/deploy production (CI & manual), lần đầu và các lần vá lỗi sau. Cập nhật: 2026-10-17.

1. Tổng quan hệ thống

SMYou Pro quản lý luồng đơn hàng → đầu việc kỹ thuật cho công ty bán/lắp máy tính, máy in, camera an ninh. Luồng lõi: Sale tạo đơn → Quản lý kỹ thuật tạo task & giao người → Kỹ thuật viên nhận/từ chối → thực hiện → khách ký xác nhận → đơn hoàn tất.

Kiến trúc: modular monolith — 1 backend FastAPI, 1 SPA React, 1 PostgreSQL — chạy bằng Docker Compose. Production đứng sau nginx hệ thống của server, phục vụ dưới subpath https://ilabsviet.com/smyoutask/.

Browser (mobile/desktop) │ HTTPS (ilabsviet.com, TLS do nginx hệ thống) ▼ [nginx hệ thống] — forward nguyên path /smyoutask/*, KHÔNG strip │ 127.0.0.1:6890 ▼ ┌─────────────── container "web" (nginx, image smyou-web) ───────────────┐ │ /smyoutask/ → static SPA (frontend dist, React Router) │ │ /smyoutask/api/ → strip prefix → proxy → backend:8000/api/ │ └──────────────────────────────┬───────────────────────────────────────┘ ▼ container "backend" (FastAPI + uvicorn, image smyou-backend) │ (sync SQLAlchemy, psycopg3) ▼ container "db" (PostgreSQL 17, volume pgdata) │ container "backend" cũng đọc/ghi volume "uploads" (/data/uploads — ảnh phiếu xác nhận, đính kèm)

Hai bộ containers tách biệt hoàn toàn theo môi trường: compose.dev.yml (Mac M2, hot reload, build local) và compose.prod.yml (AlmaLinux, chỉ pull image có sẵn, không build trên server).

3. Cấu trúc thư mục & ranh giới module

backend/ app/ main.py # create_app(), routers, exception handlers core/ # config, db, security, errors, spec_loader, authz modules/ identity/ catalog/ customers/ orders/ dispatch/ files/ audit/ notifications/ reporting/ # mỗi module: domain.py (thuần Python) · models.py (ORM) # schemas.py (Pydantic) · service.py (use case, transaction, audit) # router.py (HTTP mỏng) · queries.py (đọc có áp scope) tests/ unit/ integration/ stateful/ contract/ generated/ frontend/ src/ app/ # router, AppShell, menu.ts, auth guard components/ui/ # Button, Badge, StatusBadge, Sheet, DataList, MoneyText... features// # api.ts (hooks), components/, pages/, schemas.ts (zod) lib/api/ # schema.d.ts sinh tự động + client e2e/ # Playwright spec/ # state_machines.yaml, permissions.yaml — NGUỒN SỰ THẬT máy đọc được scripts/ # check_ac_coverage.py, export_openapi.py, deploy.sh, golive_check.sh...

Ranh giới bắt buộc (kiểm tra tự động bằng import-linter, chạy trong make lint):

  • domain.py không import gì ngoài stdlib + domain module khác — là logic nghiệp vụ thuần, không đụng FastAPI/SQLAlchemy.
  • router.py không import models.py trực tiếp — chỉ gọi qua service.py.
  • Module A chỉ gọi module B qua hàm public của B.service, không đọc thẳng B.models (trừ vài ngoại lệ đã ghi nhận và test trong ARCHITECTURE.md §3 — ví dụ audit/orders được phép đọc identity.models.Employee để join tên).

Vi phạm ranh giới làm make lint fail ngay — không "để sau sửa".

4. Luồng xử lý & luồng dữ liệu

4.1 Luồng một request điển hình

  1. Browser gọi fetch qua hook trong features/<x>/api.ts (TanStack Query) — FE không gọi fetch trực tiếp trong component.
  2. Request đi qua nginx hệ thống → container web (nginx) → nếu path khớp /api/ thì strip prefix và proxy sang backend; ngược lại trả static SPA (fallback index.html cho client-side routing).
  3. FastAPI nhận request tại router.py của module — tầng này mỏng: parse input → require("capability") dependency kiểm quyền → gọi service.py → trả response theo response_model.
  4. service.py mở transaction (qua dependency get_uow()), gọi logic thuần trong domain.py (tính tiền, validate guard, suy ra trạng thái), ghi DB qua models.py, ghi 1 dòng vào audit_events, rồi commit.
  5. Response JSON (snake_case) trả về; FE qua openapi-fetch với type sinh sẵn từ OpenAPI, TanStack Query cache theo key, sau lệnh ghi thì invalidateQueries để refetch.
Không có API nào nhận PATCH status tự do. Mọi chuyển trạng thái là lệnh có tên: POST /orders/{id}/submit, POST /assignments/{id}/reject… kèm version (optimistic lock chống ghi đè).

4.2 Luồng nghiệp vụ lõi (đơn → task → KPI)

1. Sale/Manager tạo ĐƠN (orders) └─ dòng đơn SNAPSHOT tên/mã/giá/VAT/bảo hành của sản phẩm-dịch vụ tại thời điểm tạo (đổi danh mục sau này không ảnh hưởng đơn cũ — ADR-004) 2. Quản lý kỹ thuật tạo TASK (dispatch) cho đơn, giao ASSIGNMENT cho kỹ thuật viên └─ trạng thái task là DỮ LIỆU SUY RA từ assignment chu kỳ hiện tại (ADR-007) — tính lại mỗi transaction, không tin giá trị lưu cũ 3. Kỹ thuật viên NHẬN / TỪ CHỐI assignment → thực hiện → đánh XONG └─ cần bằng chứng: ảnh phiếu xác nhận gắn revision_no (ADR-005) 4. Khách KÝ XÁC NHẬN → đơn HOÀN TẤT └─ có thể "Chỉnh sửa" → mở lại task, ghi defect_records cho KPI Mọi bước 1-4 → ghi audit_events (append-only, bất biến) └─ KPI/dashboard tính lại từ audit_events + assignments + defect_records (không tính trực tiếp trên bảng trạng thái hiện tại — ADR-006)

4.3 State machine & phân quyền — nguồn sự thật bằng dữ liệu

State machine

spec/state_machines.yaml là nguồn sự thật. Backend đọc lúc khởi động (core/spec_loader.py); domain.transition(entity, command, ctx) tra bảng, chạy guard theo tên (GUARDS[name]). Guard thiếu implementation → app không khởi động được (bắt lỗi sớm bằng test).

Permission

spec/permissions.yaml định nghĩa role → capability + scope. require("capability") trả Actor(id, roles, capability, scopes); mọi query đọc áp apply_scope(query, actor, RULES) — scope không khai báo luật = không trả dòng nào.

Frontend không tự suy luận quyền hay trạng thái cuối. Nút hành động chỉ hiện khi backend trả kèm allowed_commands cho aggregate đó; GET /api/v1/me trả capabilities + counters để FE dựng menu.

4.4 Thông báo realtime & Web Push — luồng ngoài request/response

notifications.service._create() ghi 1 dòng `notifications` └─ sau khi transaction COMMIT thành công (hook `after_commit`, cùng điểm cho cả 2 kênh dưới) ├─ 1. WebSocket (realtime.py) — đẩy ngay cho tab đang mở, kết nối còn sống │ (nguồn sự thật cho in-app; FE invalidateQueries khi nhận message) └─ 2. Web Push (push.py) — gửi tới MỌI push_subscriptions của recipient_id đồng bộ, cùng thread với request gốc, timeout 5s/thiết bị └─ cần Settings.VAPID_PUBLIC_KEY/VAPID_PRIVATE_KEY đã cấu hình, nếu không thì no-op hoàn toàn (tắt theo mặc định) └─ 404/410 (thiết bị đã gỡ đăng ký) → xoá dòng push_subscriptions, không retry └─ lỗi gửi khác không làm lệnh nghiệp vụ gốc fail (đã commit trước đó)

Đăng ký nhận Web Push (client)

Trang "Cá nhân" (/ca-nhan) gọi navigator.serviceWorker.register('/sw.js') rồi pushManager.subscribe({applicationServerKey: vapid_public_key}) (frontend/src/features/notifications/webPush.ts). Trình duyệt trả {endpoint, keys: {p256dh, auth}} → gửi lên POST /notifications/push-subscriptions, lưu vào bảng push_subscriptions (khoá theo endpoint, không theo nhân viên — 1 thiết bị = 1 dòng). frontend/public/sw.js xử lý event push (hiện notification OS) và notificationclick (mở/focus tab, điều hướng /orders/{entity_id}).

Khi nào tắt hoàn toàn

Thiếu VAPID key ở server, hoặc trình duyệt không hỗ trợ Push API (vài Safari cũ) → nút "Nhận thông báo trên thiết bị này" ẩn hẳn, không ảnh hưởng kênh in-app/WS đã có. Đây là kênh "tiện lợi thêm" khi đã đóng tab/app — không retry/queue khi gửi thất bại vì lý do khác 404/410 (chỉ log cảnh báo).

Chi tiết đầy đủ + Acceptance Criteria: docs/specs/M7-03-notifications-realtime-ws.md (WS) và docs/specs/M10-05-web-push-notifications.md (Web Push).

4.5 Sinh khoá VAPID (bắt buộc để Web Push hoạt động)

VAPID (Voluntary Application Server Identification) là cặp khoá để dịch vụ push của trình duyệt (FCM/Mozilla/Apple) xác nhận chính server này được phép gửi tới một endpoint đã đăng ký. Thiếu cặp khoá này, toàn bộ Web Push là no-op (mục 4.4) — không lỗi, chỉ đơn giản là tắt.

Dev và production phải dùng 2 cặp khoá khác nhau, sinh riêng cho mỗi môi trường. Không copy khoá dev sang prod, không commit khoá PRIVATE vào git.

Bước 1 — Sinh khoá

Script có sẵn trong repo: backend/scripts/generate_vapid_keys.py (dùng thư viện py_vapid, sinh khoá EC theo chuẩn P-256).

cd backend
uv run python scripts/generate_vapid_keys.py

Output ra đúng 2 dòng, dạng KEY=value sẵn để dán vào file env:

VAPID_PUBLIC_KEY=BF7c...(87 ký tự, base64url, không padding)
VAPID_PRIVATE_KEY=3K9z...(43 ký tự, base64url, không padding)

Mỗi lần chạy script sinh ra 1 cặp khoá mới — chạy 2 lần sẽ ra 2 cặp khác nhau. Không có lệnh "xem lại khoá cũ"; nếu mất khoá thì phải sinh cặp mới và toàn bộ push_subscriptions hiện có sẽ không nhận được push nữa cho tới khi người dùng bấm "Nhận thông báo" lại (khoá public đổi → applicationServerKey đổi → subscription cũ không còn khớp).

Bước 4 — Xác nhận đã nhận khoá

  1. Gọi GET /api/v1/me (đã đăng nhập) — response phải có field vapid_public_key khác null. Nếu vẫn null: biến chưa nạp đúng (restart lại container, kiểm tra tên biến không gõ sai).
  2. Vào /ca-nhan trên trình duyệt — nút "Nhận thông báo trên thiết bị này" phải hiện (trước đó ẩn vì vapid_public_key là null). Push API chỉ hoạt động trên HTTPS hoặc localhost, không chạy trên HTTP thường.
  3. Bấm nút, cho phép notification ở trình duyệt, rồi trigger 1 notify_* thật (ví dụ Sale submit 1 đơn cho kỹ thuật viên đã đăng ký) → kiểm tra notification hệ điều hành có hiện, kể cả khi đã đóng tab.

5.2 Quy ước bảng/migration

  • Bảng số nhiều snake_case; FK <entity>_id; index mọi FK và cột lọc.
  • Enum lưu varchar + CHECK constraint (dễ migrate hơn PG enum).
  • created_at/updated_at timestamptz default now() — lưu UTC, hiển thị giờ Asia/Ho_Chi_Minh.
  • Không xoá cứng dữ liệu nghiệp vụ — dùng is_active/cancelled_at.
  • Migration Alembic: tên YYYYMMDD_HHMM_<mô_tả>.py, luôn có downgrade(), không sửa migration đã merge.
  • Migration phải tương thích ngược 1 phiên bản (expand → migrate → contract) để rollback image không phá DB khi deploy.
# Tạo migration mới
make migration name=add_something

# Áp migration vào DB dev
make migrate

# Kiểm tra upgrade → downgrade -1 → upgrade + drift model/migration (chạy trong make check)
make migrations-check

Không mở thêm port DB ra ngoài server production (không SSH tunnel để lộ 5432) — kể cả tạm thời. Mọi truy vấn maintain chạy qua exec db psql ngay trên server.

Backup/restore đã có sẵn (xem docs/architecture/DEPLOYMENT.md): cron 01:00 hằng ngày chạy pg_dump -Fc → /opt/smyou/backups/db-YYYYMMDD.dump, giữ 14 bản; scripts/restore_check.sh kiểm tra khôi phục hằng tháng; bước deploy luôn pg_dump trước khi docker compose up.

5.4 SQL mẫu cho maintain

-- 1. Lịch sử audit của 1 đơn hàng cụ thể
SELECT seq, occurred_at, actor_id, event_type, entity_type, entity_id
FROM audit_events
WHERE entity_type = 'order' AND entity_id = '<order-uuid>'
ORDER BY seq;

-- 2. Nhân viên đang bị khoá đăng nhập
SELECT id, code, full_name, email, failed_login_count, locked_until
FROM employees
WHERE locked_until IS NOT NULL AND locked_until > now();

-- 3. Thiết bị đã đăng ký Web Push của 1 nhân viên
SELECT id, endpoint, created_at
FROM push_subscriptions
WHERE employee_id = '<employee-uuid>';

-- 4. Đếm đầu việc (task) theo trạng thái hiện tại
SELECT status, count(*) FROM tasks GROUP BY status ORDER BY count(*) DESC;

-- 5. Giá trị code_sequences hiện tại (kiểm tra trước khi nghi ngờ sinh mã bị lệch/trùng)
SELECT scope, period, last_value FROM code_sequences ORDER BY scope, period;

-- 6. Thông báo chưa đọc của 1 nhân viên
SELECT id, type, title, created_at
FROM notifications
WHERE recipient_id = '<employee-uuid>' AND read_at IS NULL
ORDER BY created_at DESC;

6. Backend / API

Danh sách màn hình → API → bảng DB đầy đủ nằm ở §5.1. Phần này là quy ước áp dụng cho mọi endpoint, không lặp lại danh sách.

  • Tiền tố /api/v1, JSON snake_case, ID là UUID (hiển thị dùng code).
  • CRUD list: GET /x?q=&limit=&offset= → { items, total, limit, offset }, limit ≤ 100.
  • Lỗi theo RFC 9457 application/problem+json: 
    { "type": "about:blank", "title": "...", "status": 409,
  "code": "INVALID_TRANSITION",
  "detail": "Thông điệp tiếng Việt cho người dùng",
  "errors": [{ "field": "reason", "code": "too_short" }] }
    Mã chuẩn: VALIDATION_ERROR 422, UNAUTHENTICATED 401, FORBIDDEN 403, NOT_FOUND 404, INVALID_TRANSITION/GUARD_FAILED/STALE_VERSION/CONFLICT 409, FILE_REJECTED 415/413.
  • Mọi route khai báo response_model, summary, operation_id (dạng orders_submit) → client TS sinh tên ổn định.
  • Logging JSON có request_id; không log mật khẩu, token, số điện thoại đầy đủ.
  • Cấu hình qua biến môi trường (.env) — không hard-code secret trong code.

7. Frontend

Mỗi route/màn hình ở §5.1 là 1 thư mục trong features/<x>/ theo đúng tên module backend tương ứng (ví dụ route /dispatch/* → features/dispatch/ → module backend dispatch).

  • Trang = features/<x>/pages/*Page.tsx; không gọi fetch trực tiếp, luôn qua hook trong api.ts.
  • Trạng thái server quản lý bởi TanStack Query, key dạng ['orders', params]; sau lệnh ghi → invalidateQueries.
  • Hiển thị trạng thái qua <StatusBadge machine="order" status={...}/>, nhãn/màu đồng bộ với spec/state_machines.yaml (có test so khớp, tránh lệch khi spec đổi).
  • Mỗi trang có đủ 4 trạng thái UI: loading (Skeleton), empty (EmptyState + CTA), error (thông điệp + thử lại), success.
  • Form dùng zod schema; lỗi 422 từ server map thẳng vào field lỗi.
  • Không any, không dùng useEffect để fetch dữ liệu.
  • Mobile-first: thiết kế từ 390px rồi mới md:/lg:; vùng chạm ≥ 44px; icon dùng lucide-react.

11.2 Cấu hình nginx hệ thống (subpath /smyoutask/)

Server dùng chung nginx hệ thống giữ HTTPS cho ilabsviet.com và proxy nhiều app theo subpath. Thêm khối cấu hình (đã có sẵn mẫu + test tự động khớp nội dung ở ops/nginx/smyoutask.conf) vào file nginx của ilabsviet.com:

upstream smyoutask_ilabsviet {
    server 127.0.0.1:6890;
}

location = /smyoutask { return 301 /smyoutask/; }
location /smyoutask/ {
    limit_req zone=perip burst=20 nodelay;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header Host $host;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection 'upgrade';
    proxy_pass http://smyoutask_ilabsviet;   # KHÔNG có "/" cuối — giữ nguyên prefix
    proxy_connect_timeout 59s;
    proxy_read_timeout 120s;
    proxy_send_timeout 120s;
    proxy_hide_header X-Powered-By;
    proxy_redirect off;
    client_max_body_size 12M;   # ảnh phiếu xác nhận ≤ 10MB
}
nginx -t && systemctl reload nginx
Bắt buộc có proxy_set_header X-Real-IP $remote_addr; ở khối nginx hệ thống — container web thay thế (không nối thêm) X-Forwarded-For dựa trên giá trị này; nếu thiếu, khách có thể tự gửi header giả IP.

Mục đích của make smoke-prod

Đây là buổi tổng duyệt của chính 2 image vừa build bằng make build-prod, chạy bằng đúng compose.prod.yml sẽ dùng khi deploy thật — nhưng chạy ngay trên Mac, dùng giá trị test từ .env.prod.example (không phải secret thật), project Docker riêng smyou-smoke (không đụng tới stack dev đang chạy). Mục tiêu: bắt lỗi "chỉ xảy ra ở cấu hình production" trước khi tốn công docker save | ssh | docker load lên AlmaLinux — ví dụ:

  • Image build amd64 bị thiếu dependency, không khởi động được (khác hẳn môi trường dev arm64 build trực tiếp từ source).
  • Biến môi trường production (APP_ENV=production, BASE_PATH=/smyoutask, COOKIE_SECURE=true...) làm lộ lỗi mà cấu hình dev không gặp — ví dụ API docs lẽ ra phải tắt ở production.
  • Container backend chạy alembic upgrade head lúc khởi động bị fail trên image production (khác migration chạy tay lúc dev).
  • Subpath /smyoutask nướng sẵn vào bundle FE/nginx của image web lúc build — route sai subpath chỉ lộ ra khi test đúng bằng image đã build, không lộ lúc chạy dev ở root path.

Chạy cụ thể: docker compose -f compose.prod.yml --env-file .env.prod.example -p smyou-smoke up -d --wait rồi chạy bộ test backend/tests/docker (đánh dấu -m docker, loại trừ test_dev_stack.py) nhằm vào http://127.0.0.1:6890 (cổng web của stack smoke) — gồm health check, kiểm tra route qua subpath, kiểm tra response từ image thật (không phải code sống như lúc make up). Dù pass/fail, lệnh tự down -v dọn sạch stack smoke ở cuối, không để lại container/volume rác. Không chạy lệnh này nhằm vào DB production thật — nó luôn tự tạo 1 DB Postgres mới, trống, trong container riêng.

Quy trình giống lần đầu nhưng ngắn hơn — dùng scripts/deploy.sh để tự động hoá, chạy từ Mac dev:

# 2) Cấu hình đích deploy (chỉ cần làm 1 lần, không commit deploy.env)

# điền SERVER_HOST, SERVER_USER, SERVER_PATH=/opt/smyou

# 3) Deploy — script tự: dump DB trước khi đổi, save/load image qua ssh,
#    copy compose.prod.yml, sed IMAGE_TAG, "up -d --wait", rồi curl healthcheck
scripts/deploy.sh 2026.10.20-1
Lệnh scripts/deploy.sh 2026.10.20-1 gõ và Enter trên Mac dev — đúng 1 lệnh, không cần tự SSH trước. Bản thân script chứa nhiều lệnh ssh server '...' bên trong, tự nhảy qua server khi cần rồi quay lại — không phải chạy trực tiếp trên server. File set -euo pipefail ở đầu script: bất kỳ bước nào lỗi, script dừng ngay tại đó, không chạy tiếp các bước sau, không tự rollback bước đã làm trước đó.

scripts/deploy.sh làm gì, từng dòng (đọc trực tiếp trong repo nếu cần sửa)

  1. Validate (chạy trên Mac) — kiểm tra TAG hợp lệ (chỉ chữ/số/./_/-) và 2 image smyou-backend:$TAG/smyou-web:$TAG đã có trong docker image ls cục bộ. Thiếu image → dừng ngay, báo chạy make build-prod TAG=... trước (chưa chạm server).
  2. Đọc deploy.env (chạy trên Mac) — lấy SERVER_HOST/SERVER_USER/SERVER_PATH (file này không commit, mỗi máy dev tự tạo từ deploy.env.example).
  3. Backup DB (nhảy qua server qua ssh "$SERVER" "...") — chạy 
    docker compose -f compose.prod.yml --env-file .env.prod \
  exec -T db sh -c 'pg_dump -Fc -U $POSTGRES_USER $POSTGRES_DB' \
  > backups/predeploy-<timestamp>.dump
    ngay trên server, dump ra file trước khi đổi bất cứ thứ gì. Đây là bước hay fail nhất — xem hộp cảnh báo dưới.
  4. Chuyển image (chạy trên Mac, đẩy dữ liệu qua ssh) — docker save backend_image web_image | gzip | ssh "$SERVER" 'gunzip | docker load': nén 2 image thành 1 luồng byte, bơm qua kết nối SSH, phía server gunzip rồi docker load thẳng vào Docker engine — không ghi file tạm, không cần registry riêng (GHCR/Docker Hub).
  5. scp compose.prod.yml (từ Mac lên server) — phòng trường hợp file compose đổi so với lần deploy trước.
  6. Đổi tag + khởi động lại (nhảy qua server) — 
    sed -i "s/^IMAGE_TAG=.*/IMAGE_TAG=$TAG/" .env.prod
docker compose -f compose.prod.yml --env-file .env.prod up -d --wait
    sed ghi đè đúng dòng IMAGE_TAG=... trong .env.prod thành tag mới, rồi up -d --wait mới thực sự restart container thật (có downtime ngắn ở đây) — container backend tự chạy alembic upgrade head khi khởi động lại, không cần chạy migration tay.
  7. Healthcheck (nhảy qua server) — curl -fsS http://127.0.0.1:$WEB_PORT/smyoutask/api/v1/health; fail thì script thoát với lỗi, in gợi ý xem docker compose logs — không tự rollback, bạn phải tự quyết định rollback theo §13 nếu cần.
Lỗi hay gặp nhất: error while interpolating services.backend.image: required variable IMAGE_TAG is missing a value: required — xảy ra ngay ở bước 3 (backup), trước khi chạm tới image/service thật.
Nguyên nhân: compose.prod.yml khai image: smyou-backend:${IMAGE_TAG:?required} (không có default) cho cả service backend và web — cú pháp :?required buộc Compose phải có giá trị, thiếu thì lỗi ngay. Dù bước 3 chỉ cần exec vào service db, Compose vẫn phải đọc/interpolate toàn bộ file để resolve mọi service, nên nếu dòng IMAGE_TAG=... trong .env.prod trên server đang trống/mất/sai cú pháp (ví dụ bị sửa hỏng lúc chỉnh tay thêm biến khác như VAPID key), toàn bộ lệnh docker compose fail ngay từ bước đầu — chưa hề chạm tới docker load hay restart service nào.
Vì sao image mới vẫn có thể đã thấy trong docker images trên server: đó là dấu vết của một lần chạy deploy.sh/docker load trước đã tới được bước 4, không liên quan tới lần chạy bị fail ở bước 3 — server lúc đó vẫn đang chạy tag cũ, chưa deploy xong.
Cách sửa: ssh vào server, grep -n '^IMAGE_TAG=' /opt/smyou/.env.prod kiểm tra dòng này tồn tại và có giá trị hợp lệ (ví dụ tag đang chạy thật, không phải rỗng/CHANGE-ME); sửa lại nếu hỏng, rồi chạy lại scripts/deploy.sh <tag> từ đầu — docker load lại image đã có sẵn không gây hại gì, chỉ tốn vài giây.
Checklist mỗi lần deploy (DEPLOYMENT.md §9): CI xanh trên commit cần deploy (gồm job image) → pg_dump trước deploy thành công → up -d --wait healthcheck OK → đăng nhập thử 1 tài khoản mỗi vai trò.

Có registry riêng (GHCR/registry nội bộ) thì thay bước save/load bằng docker push/docker pull (--push ở buildx) — hiện repo chưa dùng registry, deploy trực tiếp qua ssh.

ssh deploy@server 'cd /opt/smyou \
  && sed -i "s/^IMAGE_TAG=.*/IMAGE_TAG=<tag_cu>/" .env.prod \
  && docker compose -f compose.prod.yml --env-file .env.prod up -d --wait'

Giải thích từng phần — <tag_cu> không phải cú pháp, phải thay bằng tag thật của bản trước (ví dụ 2026.10.20-1), lấy từ lịch sử deploy hoặc docker images trên server:

  • ssh deploy@server '...' — mọi lệnh trong cặp nháy đơn chạy trên server, không phải trên Mac; ssh giữ kết nối tới khi cả chuỗi lệnh (nối bằng &&) chạy xong rồi tự đóng.
  • cd /opt/smyou — vào đúng thư mục chứa .env.prod và compose.prod.yml; thiếu bước này sed/docker compose ở dòng sau sẽ tìm file sai chỗ.
  • sed -i "s/^IMAGE_TAG=.*/IMAGE_TAG=<tag_cu>/" .env.prod — sửa tại chỗ (-i, ghi đè luôn file) dòng bắt đầu bằng IMAGE_TAG=, thay toàn bộ phần sau dấu = bằng tag cũ. Regex ^IMAGE_TAG=.* khớp đúng 1 dòng dù giá trị hiện tại là gì — không động tới các dòng biến khác trong file.
  • docker compose -f compose.prod.yml --env-file .env.prod up -d --wait — khởi động lại container với IMAGE_TAG vừa đổi; vì image cũ vẫn còn trong docker images trên server (Docker không tự xoá khi deploy bản mới), lệnh này chạy ngay, không cần docker load lại. --wait chặn tới khi healthcheck pass.

Vì migration luôn tương thích ngược 1 phiên bản (expand → migrate → contract, §5), image cũ chạy được với schema mới hầu hết trường hợp. Nếu migration mới không tương thích → khôi phục từ dump predeploy-* mà deploy.sh đã tạo trước khi đổi (chỉ đổi IMAGE_TAG là không đủ trong trường hợp này).

Backup định kỳ

  • Cron 01:00 hằng ngày: pg_dump -Fc → /opt/smyou/backups/db-YYYYMMDD.dump; tar volume uploads; giữ 14 bản; copy ra ngoài server (rclone/NAS).
  • Mỗi tháng thử khôi phục vào DB tạm: scripts/restore_check.sh — backup chưa thử khôi phục = chưa có backup.
